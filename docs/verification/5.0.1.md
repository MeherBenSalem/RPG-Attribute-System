# RPG Attribute System 5.0.1 verification

This record lists what was checked for 5.0.1, on which source, and what was not checked. As with [5.0.0](5.0.0.md), results from one commit do not carry over to a later commit with a different tree.

## Source

The gameplay, config and workflow changes are in [`f2cb216`](https://github.com/MeherBenSalem/RPG-Attribute-System/commit/f2cb21606d67565ad9d2270041a546b1b290cd7e). The release commit adds only this record on top of it. The tagged Publish run rebuilds, stamps and re-verifies all ten JARs at the tag commit itself.

## Reports

1. **Attack Power, Protection and Toughness had no effect** for a player with about 250 mods on Forge 1.20.1. Two Protection-boosted hits still took health from 20 to 10.
2. **Config edits reset when the game was relaunched.**

## Reproduction on 5.0.0

### Attributes

A temporary server-side probe (not committed) ran inside a real Forge 1.20.1 dedicated server (`:forge:runServer`, Forge 47.2.30). It created two survival players without connections. It allocated points to one through the real `CommitAttributeAllocationProcedure`: 20 Vitality, 500 Attack Power, 500 Protection and 100 Toughness. It then measured real `hurt` and `attack` calls against a zombie.

| Measurement | No points | With points |
| --- | --- | --- |
| attack_damage | 1.0 | 101.0 |
| armor | 0.0 | 30.0 (base 125, vanilla maximum 30) |
| armor_toughness | 0.0 | 10.0 |
| 8.0 mob hit on Easy, health lost | 5.0 | 1.0 |
| Full-strength punch, damage dealt | 1.0 | 101.0 |

5.0.0 applies all three attributes in an unmodded game, and they survive a save/load relog. The report's "20 → 10 in two hits" equals the no-points row (5 per hit), so in that pack something replaced RAS's values. 5.0.0 applied each `attribute … base set` by overwriting the attribute's base value. Any mod, script or datapack that writes the same base value silently replaces it.

The specific mod in the reporter's pack was not identified; no mod list or log was available.

### Config

On the same server, four typical edits were made to the generated files between two launches:

- `attribute_2.json` saved as ANSI (cp1252) with `max_level` 30 and a new display name
- `attribute_4.json` with `max_level` 40 and a trailing comma
- `attribute_1.json` with `max_level` 50 and `on_level_event` deleted
- `attributes/settings.json` with `init_val_starting_level` 5

After relaunching, 5.0.0 had rebuilt `attribute_2.json` and `attribute_4.json` from defaults and put `on_level_event` back: four of the six edited values were lost. The log showed `Failed to read config file` and `Failed to parse config file` for the two rebuilt files. A Gson check confirmed the causes: `Files.readString` rejects the ANSI `§` byte, and Gson rejects the trailing comma even in lenient mode. A UTF-8 BOM parses fine.

## Not checked

- The reporter's modpack. The modifier approach removes the base-value conflict that matches the report. A mod that replaces the damage or armor formula itself would still decide how these values are used.
- The real client GUI for 5.0.1. No client code changed.
- Fabric players' attribute behavior on a real server. The attribute code is shared common code, verified on Forge and NeoForge; Fabric differs only in player-data storage, which uses the same `PlayerVariables` NBT.
- 26.1.2 and 26.2 on a real server. Their attribute and config code is identical to 26.3.
