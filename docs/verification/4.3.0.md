## What the focused checks cover

The rules/cache tests compile the **actual isolated production copies** with Java `--release 17` and a cached Gson jar. They cover disabled defaults, unknown-field preservation, rule precedence/ties, explicit zero, weighting gates, fractional effective armor, overflow/nonfinite values, dynamic tag predicates, unsupported schema, unreadable/malformed reloads, cached evaluation, and the actual config-studio ZIP→JSON export fixture.

```sh
python3 scripts/test-mob-xp.py --gson-jar /path/to/gson.jar
```

The configuration-studio wrapper runs the real JavaScript importer/exporter and preview, then compiles each unmodified production `MobXpRules.java`. Fresh exported JSON is compared with both shared expectations and the preview in all five roots. Schema/fixture checks are separate from that actual export/parser execution.

```sh
python3 scripts/test-mob-xp-schema.py
python3 scripts/test-config-studio.py --gson-jar /path/to/gson.jar
```

The gameplay regression harness compiles the **actual** `ConfigInitializer`, `ConfigValidator`, `MobXpConfig`, `GameplayRulesProcedure`, and `LevelingService` source with minimal Minecraft/platform test doubles. It verifies imported file preservation, corrected fresh-only stats labels, startup validation modes, dimension replacement, multiplayer shared-pool conservation/radius/dimension exclusion, vanilla/client/summon bypass, effective fractional armor, legacy player migration, reset progression, repeated sync, and rejected invalid/overflowing amounts.

```sh
python3 scripts/test-gameplay-regressions.py --gson-jar /path/to/gson.jar
```

These source-level checks are distinct from loader/API builds and in-game integration. Test-double sharing checks do not establish real multiplayer behavior. They do not prove real network packets, loader death-event cancellation/deduplication, datapack reload, physical combat, or native rendering.

Each common Gradle `check` also runs the plain-Java `mobXpTest` and `rasGuiLayoutTest` entry points. The separate layout/number-format harness checks actual isolated UI helpers; it is not pixel evidence:

```sh
python3 scripts/test-ui-layout.py
```

Build each isolated root with its required Java toolchain (17 for 1.20.1, 21 for 1.21.1, 25 for calendar-version roots). For example:

```sh
cd 1.21.1 && ./gradlew build --no-daemon
```

## Native gameplay and visual limits

The opt-in native harness runs a genuine Fabric client with an integrated server and disposable fixture. Physical mouse/keyboard input exercises the real menu and sends the normal allocation packet. Checks compare server-authoritative points/values, synced client variables, and actual Minecraft movement-speed base/effective values. Real X11 PNGs require independent human review for readability, alignment, paging, tooltips, focus, and navigation at each actual scale.

Skeleton kills are **programmatic player damage through real loader death hooks**, not physical combat attacks. Fixed cases check entity-over-tag precedence, real skeleton tag matching, Hard difficulty, effective armor, malformed-file last-good reload, and disabled-rule legacy rewards. Fixture seeding is setup; the harness does not call the award/allocation procedure directly or fabricate kill rewards with `addXp`.

Representative success does not prove multiplayer, dedicated-server gameplay, Forge/NeoForge or other-version runtime, physical combat, exhaustive cancellation/deduplication, Forge boss item drops, real admin-command/datapack reload, or arbitrary resize/container bounds. Those remain separately scoped checks. Configuration-studio source/export parity does not establish rendered-browser or hosted-Site acceptance.

## Final-commit release gate protocol

Follow [the verified release workflow](../releasing.md) before tagging or publishing:

1. Independently review the final source, including version-specific runtime behavior and documentation.
2. Pass both loaders for all five roots and every required focused job on that exact source SHA, with the correct toolchains.
3. Verify the actual complete ten-JAR inventory, source stamps, metadata, dependencies, and hashes; generate all twenty exact platform descriptors. Synthetic verifier tests or a partial prebuilt directory cannot replace this step.
4. Complete fresh genuine Fabric 1.21.1 and 26.3 launches at actual scales 2, 3, and 4 on that SHA. Require nonce/source/version identity, readiness, real packet allocation and movement-speed sync, all bounded death/reload cases, native PNG review, and clean shutdowns. A failed, skipped, clamped, stale, or mismatched case does not pass. Older evidence without the independently verified identical-tree linkage below is historical context only.
5. Any source/tree change reopens independent review and required runtime checks. Native evidence may carry across a metadata-only merge/tag SHA only after independent verification that the **entire Git tree is byte-identical** to the reviewed candidate and the main base is unchanged. Publication JARs must still be rebuilt and source-stamped for the actual merge/tag source SHA, with a newly verified hash-bound inventory and descriptors.
6. For an authorized publication, verify live provider catalogs and required dependencies, retain the hash-bound upload journal, and reconcile pending/uncertain submissions without blind retries. Completion requires all twenty matching entries to be public: Modrinth `listed` + `release`, or CurseForge available + Approved/Released. Submitted or pending-review entries are not completed public publication.

Keep commit-specific run links and immutable artifact identities with the release record. Disclose the coverage limits above even after the representative gates pass.
